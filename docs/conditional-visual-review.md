# 用途から判断する視覚レビュー

「AIっぽい」という印象は調査の入口です。作者の推定や色の禁止リストには使いません。利用者の仕事、情報の関係、操作の順序から、残す表現と変える表現を選びます。

## 二つの判定を分ける

- 必須条件：情報の欠落、誤った状態表示、操作不能、契約違反はFAIL。必須項目が未確認なら総合受入れは保留し、既存scorecardではWARNと記録する。
- 表現の提案：優先順位、まとまり、読み順、装飾の必要性を説明する。好みの差は改善提案にとどめ、CIを失敗させない。変更不要も有効な結論。

美観で必須条件の失敗を相殺しません。機械検査PASSと画面全体の受入れは別です。

## 観測から修正へ

| 徴候 | 調べること | 残す条件・反例 |
|---|---|---|
| 色のグラデーション | 意味のない強調、局所コントラスト | ブランドや量の表現に必要なら残す。紫色だけで不合格にしない |
| 発光・背景のもや | 本文や境界との競合 | フォーカス・警告・状態の識別まで消さない |
| 絵文字・アイコン | 意味、表示環境差、操作名 | 内容としての絵文字は許容。線アイコンにも名前が必要 |
| 太い見出し | 主従の競合、日本語の折返し | 太さ700を一律禁止しない。細字化で読みにくくなる反例を確認 |
| 汎用的な見出し | 対象者と完了できる仕事が分かるか | 検索・設定など共通語の再利用は正常 |
| 強い語調・実績数字 | 対象、期間、母数、比較条件と裏付け | 根拠未提示は未確認。虚偽と即断せず、数字や効果を創作しない |
| 同型カード・中央揃え | 比較・順序・階層を失っていないか | 同種比較の整列は保つ。違いを作るためだけに配置を変えない |

## レビュー記録

1. 対象版、DESIGN.md、URL、画面幅、状態、観測方法を固定する。
2. 各指摘に「場所／観測／利用者への影響の仮説／残す理由／変更案／確認方法」を書く。
3. 必須違反・推奨修正・任意提案を区別し、主たる修正先を契約・実装・検査へ割り当てる。
4. 同じデータ・機能・幅・状態で前後比較する。通常に加えて長文・空・エラーを確認する。
5. 利益と損失を併記する。余白拡大で同時比較が難しくなる、色削減で警告が埋もれる場合もある。

主張を扱うときは、表示文・根拠資料・確認時点・対象条件・確認者を記録し、確認済み／未確認／矛盾ありを分けます。スクリーンショットだけで実績の真偽や操作性を証明しません。

## 一画面で試す

[通知設定の比較例](../examples/notification-settings/README.md)では、文言と機能を共有し、主操作・補足・設定項目の関係を変えています。対象要素の計測とキーボード操作は自動検査し、情報の優先順位はレビュー記録で判断します。操作時間や満足度の改善は未実証です。
