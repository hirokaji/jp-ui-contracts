# v0.2.0 — executable contract validation

`v0.2.0` changes `jp-ui-contracts` from a collection of Japanese UI design-contract templates into a small executable validation loop.

The editable source is still `DESIGN.md`. The release adds machine-readable projection, static contract validation, reusable failure fixtures, rendered browser gates, retained Evidence, and a maintenance loop around that source.

## What changed

### Contract validation

- zero-dependency `validators/contract.py`
- strict validation for shipped templates and examples
- generated JSON projection using `schema/design-contract.schema.json`
- unit tests for parser and hard validation behavior

`DESIGN.md` remains the file humans edit. The JSON form is generated for CI and agents rather than maintained as a second contract copy.

### Failure fixtures

Seven repeatable Japanese UI failure surfaces are included and CI-gated:

- long Japanese paragraphs
- mixed Japanese / English headings
- long URL and machine-token overflow
- Japanese forms, IME, helper text, and errors
- dense tables
- narrow mobile wrapping
- technical documentation mixing prose, inline code, code blocks, callouts, and tables

Each fixture has explicit PASS / WARN / FAIL criteria.

### Rendered validation

Playwright 1.63.0 renders every required fixture in:

- desktop Chromium at 1440px width
- a Pixel 7 mobile profile explicitly bound to Chromium

Automated gates cover document-level horizontal overflow plus fixture-specific structural properties such as local table/code scrolling, inspectable form semantics, and minimum mobile action height.

Full-page screenshots, render metrics, failure traces, and the Playwright HTML report are retained as CI Evidence.

## A useful failure found while building v0.2

The first rendered-validation run failed before testing the UI.

The mobile project used an iPhone device descriptor, which selected WebKit, while CI installed Chromium only. The failure was attributed to the validation runtime rather than to the UI contract or fixture. The project was corrected to a Pixel 7 profile explicitly bound to Chromium, then the same gates passed.

This is an example of the release's intended loop:

```text
failure
→ Evidence
→ attribution
→ change the owning layer
→ re-run
```

## Maintenance changes

- full validation runs weekly even when no code changes occur
- manual `workflow_dispatch` is available
- Dependabot proposes npm / Playwright and GitHub Actions updates
- `AGENTS.md` gives coding agents the repository mission, guardrails, and definition of done
- pull requests use an Evidence-oriented template

## Upgrade from v0.1.0

Existing `DESIGN.md` files do not need to be replaced with JSON.

Start with static validation:

```bash
python validators/contract.py validate DESIGN.md
```

To run the repository's rendered fixture gates:

```bash
npm install
npx playwright install chromium
npm run test:rendered
```

## Compatibility and non-goals

This release does not claim universal Japanese typography correctness, cross-browser equivalence, or pixel-perfect visual regression.

The first `v0.2.0` gate deliberately focuses on repeatable structural failures that can be measured with the current Chromium harness. Firefox / WebKit hard gating, pixel baselines, automated visual-diff approval, package-manager distribution, and a hosted fixture gallery remain later decisions.

## Release gate

The exact acceptance conditions are defined in [`docs/v0.2-release-gate.md`](../v0.2-release-gate.md).

Before tagging `v0.2.0`, the final main commit containing the release manifest must pass:

1. strict contract validation
2. fixture completeness
3. desktop/mobile rendered validation
4. Evidence artifact creation
5. documentation consistency

## Rollback

The previous public release is `v0.1.0`.

`v0.2.0` keeps `DESIGN.md` as the editable source, so users can continue using existing contracts even if they do not adopt the new validator or rendered harness immediately.
