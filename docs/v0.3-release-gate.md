# v0.3 Release Gate — local UI validation

Version: **v0.3.0**, adding the local-URL UI checker and executable onboarding guide. This gate is implemented by the manually invoked `publish-release` workflow and `scripts/publish_release.py`. Publication status is recorded in the GitHub Release, not inferred from this document.

## Scope and acceptance

Retain Gates A–E from [the v0.2 gate](v0.2-release-gate.md): seven strict contracts, complete required fixtures, desktop/Pixel 7 Chromium checks, Evidence, and consistent documentation. Add the following requirements for the new CLI:

- `npm run test:cli` passes argument-validation tests.
- `npm run test:rendered` exercises the CLI through its actual subprocess interface: intentional overflow is FAIL/exit 1; repaired output at 412px and 1440px is PASS/exit 0; HTTP errors, missing readiness, connection failure and cross-origin redirects are ERROR/exit 2.
- Repeated executions preserve separate screenshot/JSON Evidence directories.
- The clipped-content counterexample remains explicit: document overflow PASS does not mean complete UI approval.
- Existing fixture coverage is not reduced. The current suite has 27 passing tests and one intentional desktop skip for a mobile-only target-height assertion. Any count change must identify the changed coverage.
- Publication verifies the 412px Chromium walkthrough using the CLI's 1px tolerance: before excess must be greater than 1px and after excess at most 1px. Viewport, status and overflow-check metrics must agree; actual widths are retained in the verification JSON rather than frozen to the README capture.
- README before/after captures remain traceable to a measured run. Screenshots illustrate a synthetic example; they are not a pixel-perfect acceptance baseline.

See [validation coverage](validation-coverage.md) for browser, viewport, IME, typography and accessibility limits.

## Evidence tied to the release commit

The exact commit that will receive the tag must have successful main-branch `contract-validation`, including both jobs and a nonempty `rendered-validation-evidence` artifact. A green PR run or an earlier main run alone is insufficient.

Record the commit SHA, run URL/ID, artifact ID, SHA-256 digest, test results and expiry. Download the artifact, verify its digest and ZIP integrity, and inspect screenshots, metrics and the HTML report. The current artifact lifetime is 14 days: if it expires before review, rerun validation on the same candidate. Preserve the reviewed evidence with the new release for longer-term review; recording a digest alone does not preserve the ZIP.

Avoid circular commit references: prepare metadata in the candidate commit, then record the final commit/run/artifact association in the release body or attached verification record after that commit passes. Do not mutate the candidate after its final check and reuse the old result.

## Manual publication procedure

1. Merge the reviewed release candidate PR. `VERSION`, `package.json` and root `RELEASE_MANIFEST.json` must agree on 0.3.0. The manifest remains frozen candidate metadata at the tag; actual publication state and exact commit/run/artifact association live in the GitHub Release and its attached verification JSON.
2. Wait for the exact current main SHA's `contract-validation` push run to pass both required jobs. Check its Evidence as described above. The metadata and publication safeguards add regression tests; the Python suite now has 28 tests, while the browser suite retains 27 passes and one intentional skip.
3. In Actions → `publish-release` → Run workflow, select **main**, enter its full 40-character SHA and the matching validation run ID, and leave **publish unchecked** for verification only. This validates provenance and downloads/checks Evidence without any tag/release writes.
4. After reviewing that result, run the same workflow with the same inputs and **publish checked**. The workflow requires its dispatch SHA, checkout SHA and current main SHA to match the candidate. If main moved, use the newly verified main commit/run; do not reuse the old inputs.
5. The publisher refuses a mismatched tag or an already published release. It creates a tag without force, creates a draft release, uploads the original Evidence ZIP and release-verification.json, checks asset digests/sizes, and only then publishes. A matching incomplete draft can be resumed; conflicting assets stop the process without replacing them.
6. Confirm the release URL, tag SHA, downloadable assets and verification record. Then update README/CHANGELOG publication status through a separate PR with its own CI; do not move the release tag to that follow-up commit.

`post-release-v0.2.0.yml` is now a manual, read-only retirement notice. Its original writer is retained in git history, and the complete old manifest is preserved byte-for-byte at [v0.2.0-manifest.json](releases/v0.2.0-manifest.json). The existing v0.2 publisher exits without publication when VERSION is not 0.2.0. Existing v0.2.0 notes, tag and GitHub Release are unchanged.

The new workflow has no push, schedule or workflow_run publication trigger. If an upload or final check fails, leave the release as a draft and inspect the failure. No automatic tag deletion or force-update is permitted. If GitHub Release assets are deleted later, this repository does not provide an independent archive.

## Rollback and limitations

Consumers can return to v0.2.0; existing DESIGN.md files require no migration. The local-URL CLI will be unavailable in that version. Revert a defective implementation through a reviewed PR instead of rewriting a published tag.

A real application onboarding trial is a recommended follow-up, not evidence already obtained. Native IME, Firefox/WebKit, all accessibility conditions, clipped content and arbitrary DESIGN.md conformance remain outside automated release claims.
